# Обоснование выбора языка и технологий (TECH_CHOICE)

Согласно пункту 5 регламента индивидуального проекта «Объясни задачу», для реализации основной логики, математической модели, расчётов и проверки ответов **обязателен строго типизированный язык и основанная на нём веб-технология**.

В данном проекте в качестве языка выбран **C# 12 (.NET 9)**, а в качестве веб-технологии — **ASP.NET Core Blazor WebAssembly**. Ниже представлено детальное инженерное и академическое обоснование данного выбора, а также сравнение с альтернативными технологическими стеками.

---

## 1. Сравнение C# (Blazor WebAssembly) с альтернативными платформами

| Критерий сравнения | C# (Blazor WebAssembly) *(выбран)* | Java (Spring Boot + Vaadin / Thymeleaf) | ASP.NET Core MVC / Web Forms (C#) | TypeScript + React |
| :--- | :--- | :--- | :--- | :--- |
| **Типизация** | **Строгая статическая номинативная** (C# 12, nullable reference types, readonly struct) | Строгая статическая номинативная (Java 17/21) | Строгая статическая номинативная (C#) | Статическая структурная (стирается при компиляции в JS) |
| **Язык на клиенте и сервере** | **Единый язык (C#)**: логика и рендеринг исполняются в браузере через WASM | Разделение (Java на бэкенде, JS/HTML на клиенте) | C# только на сервере; клиент требует JS или полной перезагрузки | TypeScript компилируется в динамический JavaScript |
| **Требования к хостингу (для оценки 7)** | **Нулевые**: статический хостинг (GitHub Pages / Cloudflare Pages) без серверов и баз данных | Требуется JVM-сервер (VPS, Docker, Render/Railway с ограничениями сна) | Требуется сервер с поддержкой ASP.NET Core Runtime или IIS | Статический хостинг |
| **Детерминизм вычислений** | **Полный**: точные типы `int`, `decimal`, отсутствие ошибок `0.1 + 0.2 != 0.3` | Полный (`int`, `BigDecimal`) | Полный (`int`, `decimal`) | Риск неточных чисел с плавающей точкой IEEE 754 |
| **Время отклика при пошаговой трассировке** | **0 мс (мгновенно)**: всё исполняется внутри браузера локально | Сетевая задержка (RTT) при каждом клике «Следующий шаг» | Сетевая задержка и перезагрузка страницы | Мгновенно |
| **Защита от сбоев и Null Safety** | Встроенный компиляторный анализ `<Nullable>enable</Nullable>` | Требуются аннотации `@NonNull` и внешние плагины | Зависит от версии | Strict mode |

## 2. Конкретные преимущества C# и Blazor WebAssembly для данного проекта

### 1. Единый язык и отсутствие рассинхронизации типов
В классических веб-приложениях модель алгоритма описывается на бэкенде (например, в C# или Java), а затем сериализуется в JSON для передачи в клиентский скрипт. Это создаёт дублирование типов, риск рассинхронизации структур данных и необходимость валидации на обеих сторонах.
В **Blazor WebAssembly** весь код — от структур графа блок-схемы (`FlowchartNode`, `FlowchartEdge`) и интерпретатора формул (`FlowchartExecutionEngine`) до векторного SVG-рендерера (`FlowchartViewer.razor`) — написан на **чистом C#**. Типы данных едины и валидируются компилятором Roslyn на этапе сборки.

### 2. Точная арифметика и защита от погрешностей
При анализе блок-схем критически важна абсолютная точность вычислений:
- Проверка делимости на 2: `sum % 2 == 0`;
- Проверка деления с остатком: `q = a / b`, `r = a % b`;
- Расчёт процентов скидки: `total * 0.20` и проверка порогов `total > 1000` и `final_sum >= 1200`.
В динамических языках (JavaScript) числа представлены в формате двойной точности с плавающей точкой, из-за чего выражения вроде `0.1 * 3` дают `0.30000000000000004`, что может привести к ложному ветвлению на условиях строгого равенства. В C# типизация строго контролирует диапазоны и предотвращает подобные аномалии.

### 3. Выполнение требований к публикации на максимальную оценку (7 баллов)
Пункт 7 критериев оценки требует:
> *«Приложение опубликовано и доступно по ссылке без регистрации и установки. Для публикации не нужны платный хостинг или собственный домен»*.
- Традиционные решения на Java (Spring Boot) или ASP.NET Core Server требуют постоянно работающего бэкенд-сервера. Бесплатные облачные платформы (Heroku, Render) «усыпляют» контейнеры после 15 минут неактивности, вызывая холодный старт до 50 секунд во время проверки учителем, либо требуют привязки банковской карты.
- **Blazor WebAssembly компилируется в статические файлы** (HTML, CSS, WASM бинарники .NET), которые размещаются на **GitHub Pages** с мгновенным временем отклика, доступностью 24/7 по всему миру и отсутствием затрат на серверное обслуживание.

### 4. Мгновенная реактивность при пошаговом разборе
В обучающем тренажёре ученик нажимает кнопки «Следующий шаг», «Назад», двигает ползунки и включает автопроигрывание со скоростью до 2 шагов в секунду. Выполнение расчётов прямо в WebAssembly-рантайме браузера гарантирует плавную работу со скоростью 60 кадров в секунду без сетевых лагов.

## 3. Ограничения выбранного стека и способы их компенсации

1. **Размер начальной загрузки (Initial Payload)**:
   - *Ограничение*: При первом открытии браузер загружает WebAssembly-рантайм .NET (около 4-6 МБ).
   - *Компенсация*: Использована оптимизация IL Trimming (`PublishTrimmed`), сжатие ресурсов Brotli/Gzip, а также красивый SVG-индикатор загрузки (Progress Spinner), информирующий пользователя о ходе инициализации. После первого визита все файлы кэшируются браузером.
2. **Отсутствие серверной базы данных**:
   - *Ограничение*: Статический WebAssembly-клиент не сохраняет результаты в единую серверную СУБД.
   - *Компенсация*: Для учебного проекта по чтению блок-схем постоянная база данных не требуется — состояние пользовательского сеанса и история шагов сохраняются в оперативной памяти клиента (`SimulationStateService`), обеспечивая полную приватность и отсутствие необходимости регистрации.
